# 결제처리 트랙 인수인계 (2026-11-13 시작 — 설계 단계, 구현 없음)

매출처 주문건의 결제를 다루는 섹션. 주문내역 · 계산서 · 입금 통장 · 카드결제내역(매출) · 매출처 관리를 잇는다.
마이그레이션 번호 대역: **1300번대**(2026-11-13 사용자 확정).

## 사용자가 설명한 업무체계 (2026-11-13)

- 인원은 영업지원 / 회계로 나뉜다.
- **1차(영업지원)**: 고객에게 결제 안내 전화를 하고, 해당 주문에 결제 내역을 수기로 남긴다.
  예: 11-01 하나은행 A지점 주문 → 카드결제 100,000원 진행 → 결제 내역에 "카드결제 10만원" 수기 입력.
  이때 카드번호 등 결제정보를 수기로 입력한다.
- **2차(회계 또는 다른 직원)**: 실제 결제 내역(카드 매출, 통장 입출금 등)과 매칭해 그 결제가 실제로 이루어졌음을 확인한다.
- 현재 시스템에는 결제 내역 수기 입력 기능이 없다(코드 확인: 주문에 결제 기록 필드 없음. 상담일지에만 암호화 결제정보 `payment_info_enc`).

## 현재 있는 것 (2026-11-12 코드 확인)

- 주문 ↔ 실결제: `erp_payment_matches`(bank | card | cash | prepay) — 입금 매칭 화면, 주문내역 "수금 매칭" 모달, 주문 상세 결제 내역(읽기 전용)
- 주문 ↔ 계산서: `erp_order_invoices` / 계산서 ↔ 입금: `tax_invoice_payments`
- 미수 단일 정의: `v_erp_order_receivable` + `lib/receivable.ts`
- 선결제: `erp_prepayments` + `lib/prepay.ts`
- 메뉴: `수금 · 정산 작업` 그룹(수금 대상 · 입금 매칭 · 계산서 발행 대상)

## 제안 (승인 전)

- 결제 기록(1차 수기 입력)을 새 테이블 하나로 둔다. 실결제 매칭은 기존 `erp_payment_matches`를 그대로 쓰고 기록과 연결만 한다.
- 미수는 2차 확인(매칭)에서만 줄어든다. 1차 기록은 "확인 대기" 상태로만 표시한다.
- 결제 기록은 자유 텍스트가 아니라 최소 구조(수단 · 금액 · 결제일 · 수단별 단서 · 메모)로 받는다.
- 카드번호 전체 · 유효기간은 저장하지 않는 쪽을 권고(승인번호 + 카드 뒤 4자리로 대조 가능).
- 기존 3화면은 탭으로 통합, 새 권한 그룹은 만들지 않는다.

## 사용자 결정 (2026-11-13)

1. 카드번호 수기 입력의 목적은 **대조용** → 카드번호 전체 · 유효기간은 받지 않고 **승인번호 + 카드 뒤 4자리**로 받는다("제안대로 진행").
2. 입력한 본인도 2차 확인을 **할 수 있다**(추후 변경 가능 — 막는 옵션을 나중에 넣기 쉽게 만들 것). 입력자 · 확인자는 기록.
3. 결제와 주문은 **다대다**: 주문 1건을 여러 번 나눠 결제(100만 = 20 + 30 + 50만), 결제 1건으로 주문 여러 건(10 + 50 + 40만 = 100만 1건) 둘 다 있다.
   → 결제 기록 1건(머리) + 주문별 배분 행 구조. 2차 확정 시 배분대로 `erp_payment_matches`를 만든다.
4. 1차 기록에는 **계산서 발행까지** 남긴다. 입금 내역과의 매칭이 2차 작업.
5. 기존 3화면 대체 여부는 **보류** — 사용자가 현재 화면 출력을 확인한 뒤 결정.

## 사용자 결정 2차 (2026-11-13)

1. 현금(현찰 수수) 수단은 **두지 않는다**. 수단 = 카드결제 / 계좌이체 / 계산서 발행 (+ 기존 선결제 사용).
2. 계산서 발행 기록 금액 = 주문 금액 기본값, 수정 가능, 홈택스 계산서와 다르면 불일치("가안으로 진행").
3. 확인 대기 경과 알림 = 원본 최신일 기준 3일(카드 · 이체), 계산서 발행은 입금 예정일 경과 후("가안으로 진행").
4. 확인 해제 권한 — 사용자가 "확인 해제"의 뜻 설명을 요청. 설명 후 결정 대기.
5. 기존 3화면 **권고대로 정리**: 입금 매칭 유지(결제 확인 화면의 "기록 없는 입금" 탭) / 수금 대상 → 독촉 대상(주문 단위) 탭 /
   계산서 발행 대상 → 발행 대기 주문 목록. 입금 매칭의 자동 확정은 "후보만 제시"로 바꾸는 것을 함께 제안함(별도 승인 필요).

## 사용자 결정 3차 (2026-11-13 "가안으로 진행")

1. 확인 해제 권한 = **결제 확인 화면(수금 · 정산 작업) 수정 권한자 누구나**, 사유 필수, 이력 기록.
2. 입금 매칭 "자동 매칭 실행"의 자동 확정 → **후보만 제시**로 바꾼다(3단계에서 작업).
3. 마이그레이션 번호 = **1300번대**.
4. 카드사 정산 입금 · 현금영수증 · 선결제 주문의 입금 확인은 **2차로 미룬다**.

## 구현 (2026-11-13, 1 · 2단계 — 빌드 통과, 작업 브랜치 push. main 병합 · 배포 전)

- **1300_order_payment_records.sql — 실행 · 검증 완료 2026-11-13**(사용자 회신: 테이블 3 · 매칭 record_id 1 · 결제 기록 0건 · 기존 매칭 7건).
  기존 매칭 7건은 11-05 이후 새로 생긴 수금 매칭(11-05 검증 때는 0건) — 실행 전 건수를 따로 재지 않아 "변동 없음"은 직접 대조하지 못했으나, 1300은 열 추가만 하고 행을 건드리지 않는다.
  `order_payment_records`(머리) · `order_payment_record_orders`(주문별 금액) · `order_payment_record_logs`(이력, FK 없음) ·
  `erp_payment_matches.record_id`. 미적용 상태에서도 기존 화면은 그대로 동작(결제 기록 영역만 숨김, 결제 확인 화면은 안내 문구).
- `lib/payment-records.ts` — 입력 검증(카드 뒤 4자리 외 거부) · 미결제 = 표준 미수 − 확인 대기 기록 합 · 생성/수정/삭제(확인 대기만) ·
  대기열 + 후보 찾기 · 확정(`confirmRecord`) · 확인 해제(`releaseRecord`). `SELF_CONFIRM_ALLOWED`(본인 확정 허용, 추후 변경 지점) ·
  `PENDING_ALERT_DAYS = 3`.
- 후보 규칙: 카드 = 승인번호 일치(금액 · 잔액까지 맞으면 강, 아니면 불일치) → 승인번호로 못 찾으면 금액 · ±3일 · 뒤 4자리(약).
  통장 = 금액 일치 + 날짜(이체 −3 ~ +14일, 계산서 발행일 ~ +120일), 거래처 · 입금자명 맞으면 강. 원본 잔액이 기록 금액 이상인 것만.
- 확정 규칙: 고른 원본 합계 = 기록 금액이어야 함(다르면 입력자가 기록 수정). 주문별 금액이 그 주문 미수를 넘으면 거부.
  매칭 행은 matched_by 'manual' + record_id. 거래처 없는 카드 매출은 기록의 매출처로 연결.
- API: 1차 `GET/POST/PATCH/DELETE /api/orders-portal/orders/[id]/pay-records`(주문 · 발주 수정 권한) /
  2차 `GET /api/payment-records?state=` · `POST/DELETE /api/payment-records/[id]/confirm` · `GET /api/payment-records/[id]/sources`
  (`API_OWNERS` collections, 확정 · 해제는 collections 수정 권한).
- 화면: 주문 상세 결제 내역에 `pay-records.tsx`(결제 기록 추가 · 수정 · 삭제, 같은 매출처 · 청구처 가족의 다른 주문 추가) /
  새 화면 `/payments` 결제 확인(메뉴: 수금 · 정산 작업 맨 위) — KPI(확인 대기 · 후보 있음 · 불일치 · 대기 경과) · 수단 칩 · 내가 입력한 것 ·
  확인 대기 / 확인 완료 탭 · 다른 입금 찾기 · 확인 해제.
- 다른 곳 보강: 단순 취소는 결제 기록이 있으면 409 / 취소 · 재등록은 기록의 주문을 새 주문으로 이관 /
  `DELETE /api/erp-matching`은 record_id 매칭이면 409(결제 확인 화면에서 해제하라고 안내).
- 도움말: `/payments` 항목 신설, 주문내역 변경 이력 한 줄.
- **검증 한계**: DB 키가 없어 실제 데이터로 돌려 보지 못했다. 빌드(타입 · 도움말 · UI 검사)만 통과. 1300 적용 후 사용자 시험 필요.
