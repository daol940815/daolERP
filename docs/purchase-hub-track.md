# 매입처 허브 트랙 인수인계 (2026-08 기준)

매출처 허브의 미러 — 매입처 단위로 발주·매입·지급을 통합 조회/관리하는 화면.
마이그레이션 번호는 **600번대**. 매출처 허브(총괄 세션, 100번대)를 본보기로 삼되
**코드는 복제하지 말고 새 파일로**(lib/purchase-hub.ts, app/(dashboard)/purchase-hub 등).

## 목적

- 매입처별 통합 조회: 매입 규모 · 미결제(미지급) 잔액 · 지급 이력 · 발주 이력
- "관리 안 되는 매입처" 사전 파악 (미지급 장기화, 정산 불일치)
- 사이드바 '정리 도구'에 흩어진 매입 기능(매입 사이클·미지급 Aging·매입처 관리)의 허브화

## 데이터 소스 (전부 기존 원본 — 새 원본 없음)

- 매입처 마스터: `vendors` (type='vendor'/'both') + 별칭 `erp_vendor_aliases` (alias_type='purchase')
- 매입 세금계산서: `tax_invoices` (direction='purchase') — 미지급 발생(+)
- 통장 출금: `transactions` + 매칭 — 지급(-). 기존 매입 사이클/거래처 원장 로직 참조
- 법인카드: `card_expenses` (매입처 연결분)
- ERP 주문 품목의 매입처: `erp_order_items.purchase_vendor_name` (+ purchase_alias_id) —
  발주 관점 매입 규모. 주문시스템 3단계(발주서)가 열리면 발주 이력의 원천이 됨
- 기존 리포트 로직 재사용: 미지급 Aging(`reports/payables-aging`), 거래처 정산 대조

## 선행 확정 사항 (총괄·회계 트랙에서 결정됨)

- **미결제금 기초원장**: 사용자가 관리하는 매입처별 결제현황 엑셀을 기준일 기초잔액으로
  적재하고, 기준일 이후는 매입 계산서(+)/출금 매칭(-) 원본 증분으로만 변동.
  기준일 이전 원본은 잔액 계산에서 제외(이중계상 방지).
  **적재 작업은 이 트랙이 수행** (승인 → 드라이런 → 실행 → 검증 보고 루틴).
  → 결제현황 엑셀·기준일은 사용자에게 요청할 것. docs/accounting-track.md 방침 참조.
- 매입처 기초잔액 스키마: 기존 vendor_opening_balances가 매출(수금) 중심인지 확인 후,
  매입측 확장 또는 별도 테이블을 600번대로 설계.

## 참조 패턴 (매출처 허브에서 검증된 것)

- 집계: `lib/vendor-hub.ts` — fetchAllRows/fetchAllParallel/fetchByIds(청크),
  JSONB 단일 응답 RPC(`102_hub_summary_json.sql`)로 1000행 절단·왕복 문제 해결
- 화면: 목록(KPI 카드=필터 연동 + 통합 검색 + 칩 필터) + 상세(기간칩·탭·타임라인·드릴다운)
- 상태는 데이터에서 자동 판정 (수동 상태 입력 금지)
- 담당 관리: 매입처 담당자도 contacts/contact_assignments(인물 마스터) 재사용 가능

## 검증 노트 (2026-08-10, 제주 담은 귤 사례)

- 600 마이그레이션은 사용자가 실행 완료 (hub_purchase_summary_json 동작 확인).
- "매칭했는데 미지급으로 나온다" 문의 → 원인: 해당 매입처의 2026-02-13 계산서
  51,191,000원이 미연결이었고, 건별 미지급 표시는 FIFO 배분이라 미지급이 최신(3/20)
  계산서들로 밀려 보였음. 실지급으로 보이는 출금 2건(2/27 31,191,000 + 3/6 22,595,500)은
  거래처 태깅·2001 분류까지 됐지만 계산서 연결이 없고 status='reviewed'(미확정)라
  지급으로 인식되지 않음 — 2001 상계 규칙은 060과 동일하게 confirmed만 집계(의도된 동작).
- 참고: transactions.status는 reviewed(분류됨)/confirmed(확정, 분개 생성) 2단계.
  reviewed 단계의 2001 출금을 지급으로 볼지는 060과 함께 정해야 할 미결 질문
  (현재는 양쪽 다 confirmed만 — 보수적 인식).
- **사용자 결정(2026-08-10)**: 상세 계산서 탭의 건별 지급 배지·잔여를 FIFO 대신
  **개별 연결(paid_alloc) 기준**으로 표시(완료/일부/미연결). 매입처 잔액 합계·경과기간
  막대는 기초원장 컷오프+FIFO 총액 방식 유지 — 건별 합계와 다를 수 있음을 화면에 안내.
- **사용자 결정(2026-08-10)**: 화면 노출 "Aging" 표기를 한글 "경과기간(별 현황/분석)"으로
  통일 — 매입처·매출처 허브 상세, 리포트 제목 2종, 사이드바 메뉴, 기초잔액 화면.
  경로·코드 식별자(payables-aging 등)는 유지.
- **드릴다운 수정(2026-08-10)**: 계산서 화면(?invoiceId= 딥링크) 진입 시 기간 시작일
  기본값(2026-01-01) 때문에 과거(2025-12 등) 계산서가 목록에서 빠지던 문제 —
  딥링크 진입 시에는 시작일을 비워 전체 기간을 로드하도록 수정 (허브 매출·매입 공통 효과).
- **도메인 사실 확인(2026-08-10, 사용자)**: ERP 매입가(erp_order_items.purchase_total)는
  **부가세 포함 금액**이다 (면세 상품은 세액 0이라 총액=공급가일 뿐).
  → 허브 상세 계산서 목록에서 공급가 컬럼 제거, 총액(부가세 포함)만 표기 —
  출금액 대조 기준 단일화. ERP 발주 KPI와 계산서 총액도 같은 기준이라 직접 비교 가능.
  → **매입 사이클 총액 기준 전환 완료(2026-08-10, 사용자 승인)**: 상태 엔진의
  ERP↔계산서 비교를 공급가에서 부가세 포함 총액으로 변경, TOL 0.10 → 0.05
  (실데이터 360셀 측정: 총액 기준 차이 중앙값 0.62%). 상세는
  docs/purchase-cycle-design.md v5 변경 이력 참조. 기존 확인 스냅샷은 기준 변경으로
  "재검토 필요"로 자동 전환됨(의도된 동작).

## 명칭 정리 · 두 모드 노출 · 거래처 CRUD (2026-08-14, 사용자 결정)

1. **명칭**: 사이드바 경영관리 '매입처 허브' → **'매입처 관리'**.
   이름이 겹치던 정리 도구의 `/vendors`는 **'매입처 관리(구)'**로
   (매출처의 '매출처 관리(구)'와 동일 패턴). `/vendors`는 정산 원장 기준 화면이라
   허브와 역할이 겹친다 — 나중에 흡수하고 없애는 것을 검토.
2. **두 모드 노출**: 화면 본체를 `components/purchase-hub/`로 추출해 공유하고,
   양쪽 라우트 그룹에 얇은 페이지만 둔다.
   - 회계·경영 모드 `/purchase-hub` (기존, admin 전용 레이아웃)
   - 주문 관리 모드 `/orders/purchase-hub` (신설) — 직원에게 **전체 공개**(사용자 결정).
     `(dashboard)` 레이아웃이 admin 외를 되돌려보내므로 링크 추가만으로는 안 되고
     별도 라우트가 필요했다. 공용 컴포넌트는 `basePath`(상세 링크 기준 경로)와
     `canDrilldown`(회계 모드 화면으로 나가는 링크 노출 — admin만) 두 prop을 받는다.
     주문 사이드바 메뉴에 '매입처 관리' 추가.
3. **거래처 CRUD** (`/api/purchase-hub` POST · `[vendorId]` PATCH/DELETE):
   - 등록: 목록의 '매입처 등록' 버튼. 사업자번호가 같으면 즉시 거부,
     이름이 비슷하면 후보를 보여주고 확인받은 뒤에만 생성(중복 마스터 방지 —
     롯데쇼핑 5분할 사례). 생성 시 기초원장 0원 행을 함께 만든다 —
     허브 목록은 계산서·지급·발주·기초원장 중 하나라도 있어야 잡히므로
     이 행이 없으면 등록 직후 목록에 나타나지 않는다.
   - 수정: 상세 헤더에서 거래처명·사업자번호 인라인 수정(사업자번호 중복 검사 포함).
     이메일·구분·기초원장·메모는 기존 인라인 수정 유지.
   - 삭제: **실적이 하나라도 있으면 서버가 거부**한다(계산서·통장 거래·ERP 발주 품목·
     매입 별칭·카드사 연결 확인). 삭제는 계산서·거래내역·별칭 연결을 조용히 끊고
     (SET NULL) 담당 배정·기초원장을 함께 지우므로(CASCADE) 되돌릴 수 없다.
     실적이 있으면 **비활성화**(`vendors.is_active=false`)로 정리 — 기록은 남고
     신규 선택 목록에서만 빠진다.

## 매입처 등록 폼 — 매출처와 동일 구조로 (2026-08-14, 사용자 결정)

- **점검 결과**: 필수는 거래처명 하나뿐이라 필수 조건 자체가 걸림돌은 아니었으나,
  직원이 실제로 적는 항목(업체명·지점명·담당자명·연락처) 중 폼에 있는 게 업체명뿐이라
  등록 후 상세에서 담당자를 따로 추가하는 2단계가 되는 게 문제였다.
  매출처는 이미 `orders-portal/masters` create_sales_vendor가 이 넷을 한 번에 받는다.
- **결정**: 매입처도 **업체명 + 지점명** 구조를 쓰고(거래처명 = `업체명 지점명`),
  담당자명·연락처·직함을 등록 폼에서 함께 받는다. **등록 즉시 사용 가능**(승인 단계 없음).
- **폼**: 업체명(필수) · 지점명 · 담당자명 · 직함 · 연락처 —
  사업자번호·발주 이메일·구분은 '추가 정보'로 접어둔다(구분은 회계·경영 모드에서만 노출).
- **중복 처리 (마찰 최소화)**:
  - 사업자번호 동일 → 즉시 거부
  - 이름이 정규화 기준 **완전 동일 → 확인 없이 기존 거래처 재사용**(담당자만 추가 배정).
    매출처로만 등록돼 있던 곳이면 `type`을 'both'로 올려 매입도 겸하게 한다.
  - **비슷하기만 하면** 후보를 보여주고 확인받은 뒤에만 새로 만든다(롯데쇼핑 5분할 방지).
- 지점명을 적으면 `vendor_groups`에 업체를 확보(없으면 생성)하고 그 아래 지점으로 붙인다
  — 매출처 등록과 동일 규칙. 505 미적용 환경에서는 그룹 없이 이름만으로 생성(폴백).
