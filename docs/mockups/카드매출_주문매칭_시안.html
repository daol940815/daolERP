  • · 여러 주문에 체크 + 금액 입력 = 분할 배분. 배분 합이 남은 배분액을 넘으면 저장 불가(빨간 표시). 주문 미수를 넘는 배분도 불가.
  • · 후보 정렬 = 금액 일치 → 시점(결제일 −7 ~ +60일) → 최근 주문. 합이 순액과 같은 두세 건은 "합산 가능" 표시만(자동 선택 없음).
  • · 이미 배분된 결제를 열면 현재 배분이 체크·금액 채워진 상태로 열리고, 체크를 풀면 해제된다.
동작 규칙 · 데이터
  • · DB 변경 없음: 기존 `erp_payment_matches`(source_type card)와 주문 측 배분 API(`/api/erp-matching/order`)를 그대로 쓴다. 카드번호 → 거래처 학습도 기존 규칙.
  • · 자동 매칭 없음(사용자 결정). 선택 건 일괄 처리 버튼도 두지 않는다 — 전부 모달에서 사람이 고른다.
  • · 매칭 결과는 주문 현황 · ERP 주문내역의 수금 상태(수금 매칭 모달)와 같은 데이터라 양쪽에서 같은 배분이 보인다.
  • · 매출처 허브의 미수 집계는 이 배분을 반영한다(ERP 미수 기준 규칙 그대로). 카드사 정산 입금(통장)은 별도 — 매출채권 회수로 확정.
  • · 매출 탭 KPI · 칩 · 열은 불러온 기간 안의 승인 건 기준. 취소 건 자체는 매칭 대상이 아니고 승인의 순액에만 반영.
