# 회계 트랙 인수인계 (2026-08 기준)

총괄 세션(매출처·주문 트랙)에서 진행해온 회계 업무를 별도 대화로 분리하기 위한
인수인계 문서. 결정 이력과 미결 항목을 기록한다. 규칙·원칙은 CLAUDE.md가 우선.

## 회계 처리 구조 (핵심)

- 원본(통장 transactions·법인카드 card_expenses·카드매출 card_sales·세금계산서
  tax_invoices·현금영수증 cash_receipts)을 분류·확정하면 분개가 자동 생성된다.
- 수동 분개는 조정용으로만 사용 (예: 보험료 귀속 조정). 원본은 절대 수정하지 않는다.
- 확정은 사용자가 한다. 기확정 건은 덮어쓰지 않는다. 데이터 변경은 승인 후 실행 + 검증 보고.

## 완료된 주요 결정·처리 이력

- 통장 계정과목 분류: 9개 계좌 적용 완료 — 국민, 신한, 하나 …7804(2,535건),
  기업(162건), 우리 …3633(288건), 농협(105건), SC제일(1,026건), 하나 …6204(2,609건),
  우리 …8607(881건). 사용자 작성 분류 엑셀(노란 계정과목 칸, id 키)을 대조 후 적용하는 방식.
- 오입금 처리: B안 확정 — 입금·반환 양쪽 모두 외상매출금으로 계상.
- 이체쌍(내부이체): 농협 수수료 500원 패턴 포함 자동 연결. 잔여 미연결 67건은
  미등록 계좌(급여통장 추정)와의 이체로 확정 — 해당 계좌 내역 업로드 시 해소.
- 4대보험 귀속 조정: 26년 6월에 5월분(6/1 출금)·6월분(6/30 출금)이 겹침 →
  5/31 계상 + 6/1 상쇄 수동분개(adjustment) 2건으로 5월분을 5월 판관비로 이동.
  4월분은 원래 정상.
- 계정 신설(SC 분류 때): 단기대여금, 정부보조금수익(월별손익 영업외수익 표시),
  차량운반구. 하나6204 때: 광고선전비 편입, 수선비 처리 결정.
- 하나6204 외상매입금 → 미지급금 계정 결정.
- VIP 매출 제외 조건 변경 (2026-08-06): 품명 'VIP'는 판매가=매입가 여부와 무관하게
  무조건 매출 집계 제외. 업로드 파서 수정 완료, 기존 데이터 보정 마이그레이션 401
  실행·검증 완료(잔여 0건 — 사용자 확인).
- 월별 손익현황에 기간 합계 열 추가 (2026-08-06): 화면·엑셀 모두 마지막 열에 합계.
- 통장 거래내역 화면에서 차/대변 컬럼 제거(분류 확정에 불필요 확인).
- 대량 확정: 서버 200건·클라이언트 150건 청크 처리(URL 길이 한계 대응).

## 부가세 (2026-08 개편)

- 화면: 신고서 서식 행 x 월별 열 + 신고기간 계 (`reports/vat-estimate`).
- 법인카드 매입세액 불공제: 접대비 + 차량유지비(보유 차량 K8·G80·G90·XM3 전부
  개별소비세 과세 승용차 — 사용자 확인). 미확정 건 보수적 제외.
- 현금영수증 공제 여부 미기재(NULL) = 보수적으로 불공제 처리.
- 수동 입력 항목(vat_manual_entries, 마이그레이션 106): 현금매출(원천 생기면 자동 전환
  예정), 영세율(기본 0), 대손, 경감공제, 예정신고미환급, 예정고지, 가산세.
- 카드매출은 건별 공급가액/세액 분리 저장 — 면세 건은 세액 0으로 자동 제외.

## 미수·미결제 신속 처리 방침 (2026-08 확정)

- **미수금**: ERP 주문의 collect_status/outstanding_amount(원본)가 1차 진실.
  입금 매칭은 **업로드 컷오프 규칙**으로 이중차감 방지 —
  upload 주문은 마지막 업로드(updated_at) 이후 입금 매칭만 추가 차감,
  이전 매칭은 ERP 값에 반영된 것으로 간주(연결·증빙 정보로만 사용).
  direct 주문(자체 주문시스템)은 재업로드가 없으므로 모든 매칭이 차감.
  구현: 마이그레이션 107(허브 RPC) + lib/vendor-hub.ts + ERP 주문내역 화면.
- **미결제금(매입처)**: 사용자가 관리하는 매입처별 결제현황 엑셀을
  **기준일 기초잔액(기초이월)**으로 적재하고, 기준일 이후는 매입 계산서(+)와
  출금 매칭(-)의 원본 증분으로만 변동. 기준일 이전 원본은 잔액 계산에서 제외.
  → 결제현황 엑셀·기준일 수령 대기 (적재는 승인·드라이런·검증 루틴).

### 허브 단일 진실 감사 (2026-08-12) — 지표 정의가 여러 갈래로 갈라져 있음

사용자 방침: 매출처 관련 정보는 매출처 허브, 매입처 관련 정보는 매입처 허브에 모이고
참조도 허브를 경유해야 한다. 코드 감사 결과 **모이는 것은 대체로 맞고, 참조는 거의 안
되고 있다.**

- **허브 소비자 전수**(`grep`): `lib/vendor-hub.ts`·`lib/purchase-hub.ts`를 import하는 곳은
  각 허브 자신의 API 4개(`app/api/vendor-hub`, `app/api/purchase-hub`)와 상세 화면 2개뿐.
  `hub_vendor_summary`/`hub_purchase_summary` RPC도 두 허브 lib 안에서만 호출된다.
  → 경영대시보드·경과기간분석·미수금현황·거래처별 매출 분석·수금 매칭·월별 손익은
  **전부 허브를 우회**한다.
- **미수금 정의 4가지 공존**:
  1) 허브: `outstanding - 컷오프매칭`, 상한 `LEAST(순매출)`, source 분기 有
     (`lib/vendor-hub.ts:77`, `107_hub_outstanding_cutoff.sql:40`)
  2) 전체매칭 차감(상한 없음): `lib/erp-reports.ts:492`(대시보드·경과기간분석),
     `037_receivable_reconcile_rpcs.sql:36`(미수금현황), `lib/vendor-sales-detail.ts:135`
  3) 원본 그대로(매칭 차감 없음): `lib/vendor-reconciliation.ts:104`,
     `lib/contact-manager.ts:228`
  4) 미지급금은 별도로 3가지: 허브(600/601 기초원장 컷오프) / `lib/erp-reports.ts`
     buildPayableRows(ERP 정산월 + `erp_purchase_settlements`) / 매입 사이클 상태 엔진
- **매출 정의 차이**: 허브·025·035·036·037은 취소·VIP·선결제를 제외하지만
  `lib/contact-manager.ts:227`은 `total_amount` 원본을 쓴다(담당자별 매출 과대).
  `lib/vendor-link-status.ts`도 원본 총액 기준(추정: 연결 상태 판정용).
- **기초원장 테이블 2개**: `vendor_opening_balances`(048, 매출 Aging용 — 음수로 매입까지
  겸용) vs `purchase_opening_balances`(600, 매입 기준일 컷오프용). 대시보드 미지급금은
  전자를, 매입처 허브는 후자를 쓴다.
- **source(upload/direct) 분기는 2곳뿐**: `lib/vendor-hub.ts:77`과 107 RPC.
  나머지 집계는 source를 보지 않는다 → direct 주문이 늘어나면 컷오프 규칙이
  허브에서만 맞고 나머지는 전부 틀린다(현재는 direct 주문이 적어 잠재 상태).
- **허브의 전제 조건**: 허브 RPC는 `erp_vendor_aliases.vendor_id IS NOT NULL`을
  INNER JOIN한다(107:54-57, 600:105-107, 601:73-75). 별칭 미연결 주문·품목은 허브 합계에
  아예 없다 → 허브를 단일 진실로 승격하려면 미연결 큐 해소가 선행 조건.
- **정상 사례**: direct 주문은 `lib/orders-portal.ts:306`의 `ensureAlias`로 customer 별칭을
  vendor_id까지 연결해 생성하고, 품목은 `purchase_alias_id`(268-275)를 세팅한다 →
  신규 주문도 두 허브에 정상 도달한다. 병행 운용 설계 자체는 문제가 아니다.
- 대사 스크립트: `supabase/checks/dashboard_vs_hub_check.sql`(읽기 전용) — 미수 4정의
  동시 비교, 미지급 2경로 비교, 주문 source 분포, 별칭 미연결 노출 규모 포함.

### 경영대시보드 미수·미지급 값이 컷오프를 반영하지 않는 문제 (2026-08-12 진단)

증상: "26.06까지 정산 완료 전제 · 26.07부터 반영" 컷오프 조치를 했는데 경영대시보드
미수금·미지급금에 반영되지 않음. 원인은 **집계 경로가 둘로 갈라져 있고 컷오프가 허브
경로에만 적용된 것** — 조치 자체는 실행됐다.

| 지표 | 허브 화면 (컷오프 적용) | 경영대시보드 (미적용) |
|---|---|---|
| 미수금 | `hub_vendor_summary`(107) + `lib/vendor-hub.ts` | `buildReceivableAgingRows`(`lib/erp-reports.ts`) |
| 미지급금 | `hub_purchase_summary`(600/601) + `lib/purchase-hub.ts` + `purchase_opening_balances` | `buildPayableAgingRows` → `buildPayableRows` |

- **미지급금(과대 계상)**: 대시보드는 ERP 주문 품목(`erp_order_items`)을 정산월별로 모아
  `erp_purchase_settlements`에 paid 표시가 없으면 전액 미지급으로 계상한다. monthFrom이
  null이라 26.06 이전 정산월이 전부 포함되고, 기준일 기초원장(`purchase_opening_balances`,
  406행·잔액 0)은 아예 참조하지 않는다. 기초원장 적재 드라이런의 "적재 전 양수 150곳
  17.04억"과 비슷한 과거분이 대시보드에 그대로 남아 있을 것.
  기초이월도 다른 테이블(`vendor_opening_balances` 음수분 — 매출 Aging 전용)을 쓴다.
- **미수금(과소 계상)**: 대시보드는 `erp_order_payment_matches`(026, 컷오프 없음)로 모든
  매칭을 차감한다. 업로드 이전 입금은 ERP `outstanding_amount`에 이미 반영돼 있어
  이중차감 → 미수금이 실제보다 작게 나온다. 허브의 순매출 상한(LEAST)도 없다.
- 즉 두 지표의 오차 방향이 반대다(미지급 과대·미수 과소).
- 대사 스크립트: `my-accounting-app/supabase/checks/dashboard_vs_hub_check.sql`(읽기 전용).
- 같은 경로를 쓰는 화면: 미수금 경과기간 분석(`reports/receivables-aging`)·
  미지급금 경과기간 분석(`reports/payables-aging`) 및 각 export — 함께 어긋나 있다.
- **해결 방향(사용자 결정 대기)**: (A) 대시보드·Aging이 허브 RPC를 단일 진실로 참조하도록
  전환(권장 — 정의 하나로 통일) / (B) `lib/erp-reports.ts`에 컷오프 규칙을 복제
  (규칙이 3곳으로 늘어 재발 위험) / (C) 대시보드에 두 값을 병기.

### 월별 손익현황 데이터 계보 (2026-08-13 정리)

원천이 두 갈래다. **매출·매출원가만 ERP 주문 기준**(RPC `monthly_pl_order_summary`, 025 —
`erp_orders.order_date` 기준, 취소·VIP·선결제 제외), **나머지 전부는 확정 분개 기준**
(RPC `monthly_pl_journal_summary`, 058 → `journal_lines`).

- 판관비 = 비용 계정 중 53xx 아닌 것, 영업외비용 = 53xx(`pl-report.ts:30,107`),
  영업외수익 = 수익 계정 중 4001·4004 제외 전부(`:86-87,106`). 계정별 동적 행이며
  조회 기간 전체가 0인 계정은 숨김(`:104`).
- 손익에서 제외하는 역할분리 계정: 4001·4004·5001·5002 (`:28`) — ERP 수치가 대신함.
- 미반영 3행: 급여(5101 분개 0건, `:147`) · 감가상각비(5112, `:148`) · 법인세(0 하드코딩,
  `:130,156`).
- 분개 원천 5종(source_type): `bank`(통장 — **status='confirmed'** + 계정 지정 + 이체쌍
  아님, `bank-posting.ts:57,71-72`) / `card`(법인카드 — classify_status='confirmed',
  `card-posting.ts:41`) / `card_sale` / `tax_invoice` / `manual`(조정용).
  → **확정 전 거래는 손익에 존재하지 않는다.**
- 정확도 이슈: 급여·감가상각·법인세 미반영으로 이익 과대 / '검토됨' 4,630건 미확정분이
  판관비에서 빠짐 / 매출·매출원가가 국세청 인식 기준과 다름 / 대출 이자 미반영(61건 보류).
- 산출물: `월별손익_데이터출처.xlsx`(행별 출처·분개 원천·정확도 이슈 3시트) — 사용자 전달.

### 기존 담당자 인수인계 요청서 (2026-08-13 작성)

사장님 보고용 엑셀로 정리(요청 항목 29건 = 사용자 원안 5건 + 추가 제안 24건).

  통장 적요 기재 요청 / 회계자료 수신 메일 공유 / 기존 판관비 세부내역.

  · 급여 분개가 전혀 없어 판관비 과소 계상(`pl-report.ts:147` 급여 미반영 placeholder)
