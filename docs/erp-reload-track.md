# 원본 데이터 재적재 트랙 — 인수인계 문서 (주관: ERP 총괄 세션)

사장님·사용자가 2026-10-21 제기한 "원본 데이터 전체 정리·재적재" 건. 고객관리 트랙 문서 2026-10-21 항목
(매출데이터 정리 재적재 합의, 업서트 권고, 주관 총괄 권고)을 받아 총괄이 검토 의견을 정리한다.
**상태: 검토 의견 전달, 사용자 승인 대기. 구현·삭제 미착수.**

## 사용자 질문 (2026-10-21)

1. 기존 입력된 모든 데이터 삭제 — ERP 주문내역의 오탈자·오입력이 많아 일괄 삭제 후 검수 데이터 업로드.
   끊어지는 매칭은 감수.
2. 매출처·매입처 목록 별도 관리 — 엑셀 다운로드·업로드.
3. 통장내역·계산서내역·카드사용내역도 모두 리셋 후 재업로드 — 계정과목은 키워드 자동매칭 기대,
   기존 계산서·통장입금 연결은 하지 않고 ERP의 수금완료·진행중·미수금 판정으로 처리,
   매입처 결제건은 임의 상계 후 기초잔액 입력.

## 총괄 검토 의견 (2026-10-21)

### 고객관리 트랙 2026-10-21 항목에 대한 피드백
- 사실관계·권고 모두 동의. "업서트 + 정리 파일에 없는 주문 선별 삭제"는 총괄이 2026-10-06에 낸 재적재 자문
  (덮어쓰기 권고)과 같은 결론이다. 주관을 총괄로 두는 것도 맞다 — 원본 계층 재적재는 회계·매입·주문 전 트랙에 걸친다.
- 보완 1: 문서가 "명절 판정·매입 정산 귀속"을 고아 목록에 넣었는데, 실측으로 확인된 직접 FK 손실은
  erp_payment_matches 430 · erp_order_invoices 15 · erp_prepayments 460(SET NULL)이다. 정산월 등 주문 행에 붙은
  확정값은 행이 지워지면 함께 사라지므로 "덮어쓰기면 유지, 전량 삭제면 소실"로 구분해 적는 것이 정확하다.
- 보완 2: 양식 미확정 상태라 어느 방식이든 착수 불가. **정리 파일 1건을 먼저 받아 드라이런 대조**(주문번호 일치율,
  파일에만 있는 주문, DB에만 있는 주문, 직접 주문과 겹치는 2026-07~09 건수)를 뽑는 것이 첫 단계다.

### 1. ERP 주문내역 전량 삭제 후 재업로드 — 조건부 가능, 권고는 여전히 덮어쓰기
- 사장님이 전량 삭제를 택하면 그대로 할 수 있다. 다만 "끊어지는 매칭 감수"의 실제 범위를 알고 정해야 한다:
  주문-입금 매칭 430건은 삭제되고 수동으로 다시 맞춰야 한다. 주문-계산서 연결 15건도 같다. 선결제 460건은
  주문 참조만 끊기며 재업로드 때 다시 만들어진다. 주문 행에 붙은 확정값(정산월 등)은 소실된다.
- 덮어쓰기(주문번호 upsert)로 하면 최종 상태는 같고 위 손실이 없다. 파일에 없는 주문만 선별 삭제하면
  "지우고 새로 올린 것"과 결과가 같다. 그래서 권고는 덮어쓰기지만, 결정은 사장님 몫이다.
- 어느 쪽이든 공통 조건: 직접 주문(source='direct') 5건 제외 · 삭제 범위는 source='upload'만 · 삭제 전 백업
  스냅샷(erp_orders·erp_order_items·erp_payment_matches·erp_order_invoices·erp_prepayments) · 재업로드 후 별칭
  1,734와 contact_name_links 1,400은 유지하고 미참조 별칭만 정리.
- 사용자가 든 문제 "키워드 연결 기능이 시스템을 복잡하게 만든다"에 대해: 별칭·담당자 표기 연결은 데이터를
  고치는 기능이 아니라 원본 표기를 마스터에 잇는 연결 계층이다. 정리본을 올려도 ERP가 앞으로 내보내는 표기는
  또 흔들리므로 연결 계층은 남겨 두는 것이 맞다. 정리본으로 표기가 통일되면 별칭 수는 자연히 줄어든다.

### 2. 매출처·매입처 목록 엑셀 다운로드·업로드 — 다운로드는 이미 있음, 업로드는 범위 제한으로 가능
- 다운로드: 매출처(고객관리 트랙 2026-10-01)·매입처(`app/api/purchase-hub/export`) 모두 존재.
- 업로드는 "마스터를 엑셀로 갈아 끼우기"가 아니라 **수정·추가 전용**으로 제한해야 안전하다:
  이름·사업자번호·구분·연락처·이메일·메모 수정 + 신규 추가만. 삭제·병합·id 변경은 금지(vendors를 참조하는
  FK 20곳 — 주문·계산서·통장·카드·별칭·담당자·발주 등). 삭제·병합은 기존 화면의 병합 기능으로만.
- 방식: 다운로드 양식과 같은 열 + 거래처 id 열(또는 사업자번호)로 행 식별 → 드라이런(변경될 셀 대조표) →
  승인 → 반영. 거래처 관리 수정 권한자만.
- 효과 평가: 거래처 2,279건의 오탈자 일괄 정리에는 유용하다. 다만 매출처 오류의 상당수는 vendors가 아니라
  ERP 주문의 거래처 표기(별칭)에서 온 것이므로, 1번 재적재와 함께 해야 효과가 난다.

### 3. 통장·계산서·카드 리셋 후 재업로드 — 반대
- 세 원본은 은행·홈택스·카드사가 기계로 만든 데이터라 ERP 주문처럼 오타·오입력 오염이 없다. 리셋해도 같은
  내용이 다시 들어온다. 그런데 그 위에 쌓인 사용자 확정은 전부 사라진다: 계정과목 지정 7,509 · 확정 2,828 ·
  이체쌍 2,288 · 거래처 연결 6,922 · 분개 10,550(라인 27,401) · 계산서 매칭 4,488 · 계산서-입금 매칭 3,978 ·
  카드 지출 확정 885 · 카드 매출 거래처 연결 922.
- "키워드 자동매칭으로 복원" 기대는 과하다. 키워드를 가진 계정은 50개, 기본 계정과목을 가진 거래처는 284곳이다.
  현재 지정 7,509건의 대부분은 사용자가 건별로 확정한 것이라 자동 복원 상한이 훨씬 낮다. 시스템 원칙(추천만,
  확정은 사용자)대로라면 수천 건을 다시 눌러야 한다.
- ERP 주문 삭제로 끊기는 것은 주문-입금 매칭 430과 주문-계산서 연결 15뿐이다. 통장·계산서·카드 자체와 그 사이의
  연결(계산서-입금 3,978 등)은 ERP와 무관하게 유지된다. 따라서 **ERP만 재적재하고 다른 원본은 그대로 두는 것**이
  손실 없이 목적을 달성한다.
- "기존 계산서·통장입금 연결은 안 하고 ERP 수금상태로 처리"는 매출 미수 판정의 근거를 ERP 한 곳에만 두겠다는
  뜻이다. 현재 미수 화면은 ERP 수금상태 + 주문-입금 매칭 두 근거를 쓰고 있어, 매칭을 버리면 "입금은 됐는데 ERP가
  갱신 안 된 건"을 잡을 수 없다. 재적재 후 430건 재매칭이 부담이면 1차는 ERP 수금상태로만 보고, 매칭은 미수
  확인 작업 때 건별로 다시 쌓는 운영안은 가능하다 — 다만 이는 리셋이 아니라 "재매칭을 천천히"의 문제다.
- "매입처 결제건 임의 상계 후 기초잔액 입력"은 불필요하다. 매입 결제는 계산서-통장 매칭(3,978)이 이미 있어
  미지급 잔액이 원본에서 계산된다. 임의 상계로 기초잔액을 넣으면 "집계는 원본으로 드릴다운"이 깨지고
  vendor_opening_balances(현재 0건)에 근거 없는 숫자가 들어간다. 세무사 자료와 대사할 때도 불리하다.
- 예외: 특정 계좌·기간의 통장 내역이 실제로 누락·중복이라면 그 범위만 재업로드(기존 중복 방지 로직 활용)하면
  된다. 전체 리셋은 필요 없다.

### 제안 절차 (승인 시)
1. 정리 파일 수령(양식 = 기존 업로드 양식) → 드라이런 대조표: 주문번호 일치·파일 전용·DB 전용·직접 주문 중복.
2. 사장님 결정: 덮어쓰기+선별 삭제(권고) / 전량 삭제. 후자면 손실 430·15·정산월 확인 서명.
3. 백업 스냅샷(관련 5개 테이블) → 실행 → 검증 보고(건수 대사·금액 합계·표본 20건 대조).
4. 미참조 별칭 정리 · 선결제 재생성 확인 · 담당자 자동 귀속(고객관리 트랙 파이프라인) 결과 확인.
5. 매출처·매입처 엑셀 업로드(수정·추가 전용)는 별건으로 시안 → 확인 → 구현.
6. 통장·계산서·카드는 손대지 않는다.

## 사용자 결정 (2026-10-21)

1. **ERP 주문내역 — 전량 삭제 후 정리본 업로드로 진행.** 손실 범위(주문-입금 매칭 430 · 주문-계산서 연결 15 ·
   주문 행 확정값) 인지 상태에서 결정. 삭제 조건은 위 "공통 조건"(upload 출처만 · 직접 주문 제외 · 백업 스냅샷 · 별칭·
   담당자 연결 유지)을 그대로 적용한다.
2. **매출처·매입처 엑셀 업로드 기능 — 제안 범위(수정·추가 전용, 삭제·병합·id 변경 금지, 드라이런 → 승인 → 반영)로 추가.**
3. **통장·계산서·카드 리셋 — 철회.** 손대지 않는다.

### 선행: 기존 ERP 데이터 검수 (사람 작업, 시스템 투입 전)
- 사용자 계획: ① 기존 ERP 데이터는 오입력·오탈자로 신규 ERP에 그대로 쓰기 어렵다 → ② 검수·가공 후 투입 →
  ③ 1차 검수: 오철준 대리, 홍창의 부장이 정리한 고객관리 문서를 기준으로 → ④ 2차 검수: 영업지원팀 실무자, 투입 여부 판단.
- 검수 대상 규모(2026-10-21 실측): upload 주문 8,630건(전부 2025-01-01~2026-09-30, 품목 22,968행), 직접 주문 6건(제외).
- 총괄 의견: 검수는 엑셀 위에서 사람이 하는 작업이라 **별도 세션 불필요** — 이 트랙 문서에 단계로 기록하고, 시스템은
  검수를 돕는 도구 2개만 제공한다(아래). 2번 업로드 기능은 검수와 독립이라 검수 기간에 병행 구현한다.
- 시스템 지원(총괄 구현 예정):
  a. **검수용 내보내기** — 현재 DB의 upload 주문을 기존 업로드 양식 그대로 엑셀로 내려준다(+ 참고 열: 현재 연결된
     거래처 마스터명 · 담당자 마스터명 · 별칭 상태). 검수자는 이 파일의 값만 고치고 열 구조는 바꾸지 않는다.
  b. **검수 파일 대조(드라이런)** — 검수 완료 파일을 올리면 DB와 대조해 보고서를 낸다: 주문번호 일치/파일 전용/DB 전용,
     거래처명이 vendors·별칭에 없는 건, 담당자명이 employees에 없는 건, 직접 주문과 겹치는 2026-07~09 건, 금액 합계 차이.
     2차 검수 판단 자료로 쓰고, 통과 후 같은 파일로 실제 교체를 실행한다.
- 검수 기준 권고: 거래처명은 vendors 마스터 명칭(홍창의 부장 문서가 기준 역할) · 담당자명은 employees 이름 ·
  주문번호는 기존 ERP 번호 그대로(변경 금지) · 날짜·금액 열 형식은 기존 양식 유지. 기준이 문서에 적혀 있어야 2차 검수가
  "맞다/아니다"를 판정할 수 있다.
- 범위 고정: 교체 대상은 **2025-01-01~2026-09-30 upload 주문**. 검수 기간 중 올라오는 2026-10월 이후 주문은 삭제 대상이
  아니다(현재 10월 이후 upload 0건 — 재적재 실행 시점에 다시 확인).
